- مؤشرات قواعد البيانات التي وصفها المستشار بأنها غير مستخدمة: العداد يصف فترة الإحصاءات لا حاجة العمل المستقبلية؛ لا تُحذف دون تحليل الاستعلامات.
- المكتبات المحلية الموردة: React ومكتبات التصدير والضغط ليست كودًا زائدًا لمجرد كبر حجمها. يمكن تقليل التحميل بحسب القسم بعد القياس.

## الأمان والأداء على القاعدتين الحيتين

قُرئت تنبيهات Security وPerformance للمشروعين، ثم تعريفات الحراس والدوال ذات الصلة. لم يثبت من الفحوص المنفذة تجاوز صلاحيات عام؛ هذا ليس اختبار اختراق شاملًا.

- **الحسابات/الهندسة:** مستشار الأمان أظهر `nitaq_touch` بلا `search_path` ثابت. الدالة الحية Trigger و`SECURITY INVOKER` وليست `SECURITY DEFINER`، وتستخدم `auth.uid()` مؤهلة. هذا بند تحصين منخفض الأولوية، لا ثغرة رفع صلاحية مثبتة. [مرجع التنبيه](https://supabase.com/docs/guides/database/database-linter?lint=0011_function_search_path_mutable).
- **المشروعان:** حماية كلمات المرور المسرّبة غير مفعلة بحسب المستشار. يُراجع تفعيلها حسب إعدادات الخطة. [مرجع الإعداد](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
- **دوال SECURITY DEFINER:** توجد تنبيهات تنفيذ للمستخدمين المسجلين وبعض مساعدات anon. فُحصت مساعدات الدور والهوية؛ تربط النتائج بـ`auth.uid()`، ولا يثبت التنبيه وحده تسريبًا. دالة التسجيل الجديدة Trigger؛ لا تُعامل كواجهة عادية لمجرد ظهور grant. تضييق grants غير اللازمة يكون بعد فحص الاعتماديات. [مرجع التنبيه](https://supabase.com/docs/guides/database/database-linter?lint=0028_anon_security_definer_function_executable).
- **RLS دون سياسات:** ظهرت على جداول خاصة وجداول نسخ قديمة. قد يكون المنع المباشر مقصودًا لأن الوصول عبر RPC محروس؛ لا أعتبرها تلقائيًا جداول مكشوفة.
- **CRM:** أربعة تنبيهات إعادة حساب auth داخل سياسات الصفوف، وستة تنبيهات تعدد سياسات سماح، وفهرسان لم يظهرا استخدامًا. يحتاج الحكم على أثرها خطة تنفيذ ومراعاة أن الكتابة المباشرة ممنوعة؛ بعض السياسات قد تكون بقايا توافق. [إرشاد تقليل إعادة حساب auth](https://supabase.com/docs/guides/database/postgres/row-level-security#call-functions-with-select).
- **الحسابات/الهندسة:** ثلاثة مفاتيح أجنبية دون فهرس يغطيها، وتنبيه auth على سياسة قراءة profiles، وثلاثة مؤشرات غير مستخدمة إحصائيًا. لا أضيف فهارس لكل تنبيه دون قياس الاستعلامات وكلفة الكتابة. [مرجع الفهارس](https://supabase.com/docs/guides/database/database-linter?lint=0001_unindexed_foreign_keys).
- مفاتيح `sb_publishable` الموجودة في الواجهة ليست أسرار خدمة. فحوص الحزمة الأمنية نجحت؛ لا يعني ذلك فحص كل تاريخ Git أو كل إعداد سري في الحسابات الخارجية.

## الواجهة وتجربة الاستخدام

المراجعة هنا للكود والفحوص، وليست قبولًا بصريًا بعد تسجيل الدخول في جميع الشاشات.

- تحسن موجود: بطاقات موبايل للهندسة، تصفية وصفحات، تفاصيل قابلة للإظهار، ألوان حالات مميزة مع نصوص، رسائل حفظ، وحماية مسودات عند التعارض.
- أهم مشكلة استخدام حاليًا هي عرض تحرير يسمح به الشكل ويرفضه الخادم: F02–F04. علاج الشكل وحده لا يكفي.
- تقسيم الجدول إلى صفحات لا يعالج حجم تنزيل البيانات الكامل: F06.
- المطلوب لاختبار القبول: مدير ومهندس بصلاحيات مختلفة، ديسكتوب وموبايل، لوحة مفاتيح فقط، القوائم والنوافذ المتداخلة، إغلاق Escape دون فقد إدخال، طباعة الصفوف والأعمدة المفلترة، انتهاء الجلسة أثناء التعديل، وفشل الاتصال وإعادة المحاولة.
- لا يوجد في هذا التقرير قياس Lighthouse أو قارئ شاشة أو زمن عرض من أجهزة الفريق؛ لا أنسب نتيجة نجاح للفحوص التي لم تُنفذ.

## الفحوص التي نُفذت

| الفحص | النتيجة وحدوده |
|---|---|
| `npm run check` | نجح، ويشمل تطابق البناء والمصدر والحالات والأرشيف والطباعة والربط والحفظ والصلاحيات وغيرها |
| `check:database` على PostgreSQL محلي مؤقت | نجح: الحسابات، الهندسة، CRM، الصلاحيات، CAS، إيصالات العمليات، الساعات، الحالات الجديدة، حذف المراحل وبيانات المشروع |
| `simulate:office-day` | نجح على 5000 مشروع وهمي و10 حسابات؛ تبقى فجوة قائمة التحديثات F07 |
| `npm run check:live` | نجح: واجهات الدوال والجداول وخدمة الدعوات المطلوبة موجودة؛ لا يثبت سلوك الحفظ بحسابات الفريق |
| مستشارا الأمان والأداء | قُرئا للمشروعين؛ فُصلت التنبيهات عن العيوب المثبتة أعلاه |
| فحص مراجع الدوال | حدد أربع دوال مرشحة قوية وثلاث مرشحات داخل الاستديو؛ لم يُحذف شيء |

تفاصيل قياس الضغط المحلي: قراءة 5000 مشروع منفردة نحو 1.24 ثانية في مسار الاختبار؛ عشر قراءات متزامنة p95 نحو 4.02 ثانية؛ 200 حفظ متزامن p95 نحو 164.5ms؛ 30 جولة تعديل متعارض على المشروع نفسه أعطت حفظًا واحدًا وتعارضًا واحدًا في كل جولة؛ الاسترجاع أعاد 5000 مشروع و60000 صف مرحلة مطابقين. هذه أزمنة PostgreSQL/محاكاة محلية، وليست تعهد أداء إنتاج.

سجلات الفحوص محفوظة خارج ملفات النشر في مجلد `outputs` بالمساحة المحلية: `full-audit-check-20261120.txt` و`ci-20261118-database.txt` و`ci-20261118-office-audit.txt`. بعض أسماء ملفات السجل قديمة لأن أداة التشغيل المعاد استخدامها تكتب بهذا الاسم؛ التشغيل المشار إليه هنا تم خلال هذه المراجعة.

## ترتيب التنفيذ المقترح

1. توحيد صلاحيات المتابعة والمناقصة والمستندات، مع اختبارات إعادة إنتاج مستقلة لكل عطل.
2. التحقق من نسخ إنتاج واسترجاع فعلي وتفعيل الجدول، وتصحيح دليل التشغيل.
3. إضافة سجل استعادة لتعديلات CRM المعلّقة.
4. توحيد قائمة تحديثات الاختبارات، وإضافة إعلان قدرات للخادم والنشر.
5. تقليل بيانات القراءة الأولى ومقارنات المشاريع، ثم قياس المتصفح والموبايل.
6. حذف الدوال الأربع غير المستدعاة بعد فحص الاعتماديات، وإعادة البناء والفحوص؛ بعدها تقسيم الملفات الكبيرة تدريجيًا.
7. اختبار قبول بصري ووظيفي بحسابات مخصصة، ثم تحديث سجل الإصدار.

المراجعة لم تغيّر إعدادات النسخ، أو صلاحيات الفريق، أو بيانات المشاريع، أو ملفات التشغيل. الملفات الكبيرة وتاريخ البيانات والتكامل مع خدمات خارجية تجعل «راجعنا كل شيء ولا توجد ملاحظات» نتيجة غير دقيقة؛ ما سبق يوضح الأدلة والاختبارات وحدودها.
